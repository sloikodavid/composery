### What the different models mean in practice

**OpenStack is the clearest “resource truth first” design.** A Nova server's `ACTIVE` status says something narrowly about the compute object; it does not implicitly certify the Neutron port or floating IP. Neutron independently records those resources and their statuses. This avoids a common ambiguity in VPS panels where “Running” can mean anything from “hypervisor process exists” to “we can SSH to it”. OpenStack even exposes multiple compute dimensions internally—stable VM state, current task and power state—rather than forcing one state machine to carry every meaning. ([OpenStack Docs](https://docs.openstack.org/api-ref/compute/?utm_source=chatgpt.com))

**AWS adds summary health without throwing away the dimensions underneath it.** A customer can see that the overall instance is `impaired`, but can still distinguish an AWS-host/system failure from an instance/guest failure, EBS I/O impairment, application failure or SSM management disconnection. The repair ownership follows that decomposition: AWS says a failed system check often points at underlying infrastructure, whereas an instance-status failure commonly needs customer action. ([AWS Documentation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/monitoring-system-instance-status-check.html?utm_source=chatgpt.com))

That is materially different from **Ploi's `unreachable` model**. Ploi's state is answering a very useful but different question: “Can this panel still administer the box?” If the customer disables root SSH, blocks Ploi's IPs or breaks `sshd`, the VPS may be running applications perfectly well while the panel legitimately marks the server `unreachable`. The single status is therefore primarily **control-channel health**, not resource health. ([Ploi](https://developers.ploi.io/getting-started/resource-statuses?utm_source=chatgpt.com))

**Juju shows a useful middle ground:** retain the independent facts, then optionally calculate a summary. `active/lost`-style combinations let an operator distinguish a live workload from a failed management agent, while the application-level status gives humans a simpler “blocked” signal where appropriate. ([Ubuntu Documentation](https://documentation.ubuntu.com/juju/3.6/reference/status/?utm_source=chatgpt.com)) This resembles the broader Kubernetes Conditions design: objects may report multiple independently typed conditions, while summary conditions exist to save consumers from reimplementing aggregation logic; the Kubernetes design guidance explicitly says those summary conditions should *complement*, rather than replace, detailed status. ([GitHub](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/.agents/skills/k8s-api-conventions/references/api-conventions.md?utm_source=chatgpt.com))

### Repairs that change an IP are especially revealing

There are two very different philosophies.

In **resource-oriented clouds**, the system tries to make the customer's durable network identity a separate object. OpenStack floating IPs, AWS Elastic IPs and DigitalOcean Reserved IPs can survive movement between compute instances. A “replace bad VM” repair can therefore preserve the public endpoint. ([OpenStack Docs](https://docs.openstack.org/api-ref/network/v2/index.html?expanded=list-ike-policies-detail&utm_source=chatgpt.com))

Where the ordinary VM address *is* the identifier, the system has to acknowledge that repair changes identity. AWS explicitly documents that stop/start normally gives a new ephemeral public IPv4. RunCloud documents the downstream consequence unusually clearly: after a provider-side IP change, its own stored identifier is stale, management stops working, and the new IP must be explicitly verified before the panel starts using it. ([AWS Documentation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Stop_Start.html?utm_source=chatgpt.com))

For a customer-facing panel, silently replacing an IP is therefore usually the most dangerous presentation. The observable operation is really:

`old unit: degraded → replacement resource created → customer-visible endpoint changes or is rebound → management channel re-established`

rather than simply:

`degraded → healthy`.

Terraform and Pulumi make this especially obvious because replacement is an explicit graph operation, and dependencies that consume the changed output must be reconciled. Terraform's internal design even has a notion of the old resource being “deposed” during create-before-destroy replacement; Pulumi similarly represents replacement as distinct create-replacement/delete-replaced operations. ([GitHub](https://github.com/hashicorp/terraform/blob/main/docs/planning-behaviors.md?utm_source=chatgpt.com))

### The management-access failure deserves its own state

The documentation across these products suggests three distinct cases that panels often incorrectly collapse:

1. **Provider/control-plane access intact, customer network access broken.** DigitalOcean can still offer its out-of-band Recovery Console; AWS can offer its serial console. The VM may remain fully controllable at the hypervisor level. ([DigitalOcean](https://docs.digitalocean.com/products/droplets/how-to/recovery/recovery-console/?utm_source=chatgpt.com))
2. **Guest management agent broken, VM/network otherwise healthy.** AWS SSM becomes `ConnectionLost`; Juju's agent becomes `lost`. Those systems preserve the fact that this is a management-channel failure rather than asserting that compute itself is dead. ([AWS Documentation](https://docs.aws.amazon.com/cli/latest/reference/ssm/describe-instance-information.html?utm_source=chatgpt.com))
3. **The panel itself relies on SSH/agent access and has no stronger control channel.** Ploi becomes `unreachable`; RunCloud can lose its ability to manage the box. The correct recovery is usually restoring the key, firewall rule, agent or IP mapping—not replacing the VPS. ([Ploi](https://ploi.io/documentation/ssh/can-i-safely-change-permitrootlogin-in-the-ssh-config-file?utm_source=chatgpt.com))

That last point matters operationally: **a customer-caused loss of provider management access should generally not be treated as evidence that the VM itself needs replacement**. Terraform's behavior around provisioners illustrates why: it taints after a failed *creation-time* provisioner because it cannot trust that initial construction completed, but it does not continuously replace a VM just because software inside it subsequently stops working. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/provisioners?optInFrom=terraform-io&utm_source=chatgpt.com))

So the strongest pattern I found is: **keep authoritative component states separate—compute, network identity/connectivity, storage and management channel—and derive a customer-facing `healthy/degraded/blocked` summary from them.** A top-level degraded state is useful, but systems such as Juju, AWS and the Kubernetes Conditions design show why it is much safer when the underlying reason remains first-class. Systems such as Ploi demonstrate the opposite trade-off: a compact `unreachable` state is simple and actionable, but it intentionally loses information about whether the underlying VPS and workload are actually healthy.
