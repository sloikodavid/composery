### The UX pattern

The strongest wording is the wording that names **the broken relationship rather than the machine**. AWS's **“SSM Agent is not online”**, ServerPilot's **“Not connected”** plus its definition, Plesk's newer **“Connection blocked”**, and Ploi's new SSH-stage debugger all make it comparatively difficult to conclude that the workload itself is dead. Ploi is especially notable because its September 2026 update exposes the actual last SSH error and tests each layer of the management path independently. ([AWS Documentation](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-troubleshooting.html?utm_source=chatgpt.com))

The weakest wording is **“server unavailable/offline/disconnected” without immediately naming whose connection is unavailable**. Plesk has the clearest demonstrated failure of that model: it emailed that the *server* was unavailable while its own system showed the server active. Forge's **“Server disconnected”** is less bad because its documentation now clearly says Forge may be unable to connect even while the operator can still SSH, but that qualification is in troubleshooting material rather than inherent in the status label. ([Plesk Support](https://support.plesk.com/hc/en-us/articles/25856348231959-Email-notification-received-from-Plesk-360-360-Monitoring-Your-server-is-unavailable-from-Plesk-360-August-23-2024?utm_source=chatgpt.com))

Azure is an interesting middle case. **“Virtual machine agent status is not ready”** is technically scoped correctly—it says *agent*—but it is presented as a persistent warning even when the customer intentionally opted out of having an agent. Microsoft has acknowledged another adjacent portal label can be misleading in precisely that scenario. ([Microsoft Learn](https://learn.microsoft.com/en-us/answers/questions/5490504/cant-make-the-error-message-go-away-virtual-machin?utm_source=chatgpt.com))

Finally, **Google and Cloudways are useful negative cases**. Google does not appear to present a single scary “VM offline because agent heartbeat disappeared” label; the failure generally appears at the capability being used, such as SSH, and its troubleshooter separately checks whether the VM is actually running. Cloudways does not publicly expose a comparable agent-channel state at all, so claiming a particular “Cloudways agent offline” warning would go beyond the available evidence. ([Google Cloud Documentation](https://docs.cloud.google.com/compute/docs/troubleshooting/troubleshooting-ssh-errors?utm_source=chatgpt.com))

If the design question behind this survey is what wording a management panel should use, the evidence points toward something like **“Management connection unavailable — server services may still be running”**, followed by the last successful contact and the failing layer (DNS/TCP/SSH/auth/agent), rather than **“Server offline.”** That conclusion is a UX synthesis from the products above, not wording used by any one vendor.
