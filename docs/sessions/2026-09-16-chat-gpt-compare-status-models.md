### Kubernetes Conditions: deliberately extensible, deliberately not a universal state machine

The API conventions are more restrictive than many implementations inspired by them. A Conditions collection is supposed to behave like a map keyed by `type`; controllers should establish the conditions they own even when their value is initially `Unknown`; absence of a known condition is generally interpreted like `Unknown`. Conditions describe **observations**, and the conventions explicitly say they are not themselves a comprehensive state machine. ([GitHub](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/.agents/skills/k8s-api-conventions/references/api-conventions.md))

The important consequence for a compound provider object is that Kubernetes never gives you a rule equivalent to “take all conditions and make the worst one the object's state.” It expressly rejects that as a generic operation: some conditions are normal when `True`, some when `False`, and APIs may have conditions that are informational rather than readiness gates. A top-level `Ready` or `Available` is therefore another piece of domain logic, not a built-in reduction operator. ([GitHub](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/.agents/skills/k8s-api-conventions/references/api-conventions.md))

Kubernetes also distinguishes two kinds of time that are easy to conflate. `observedGeneration` says “this judgment was made against the current desired object generation”; `lastTransitionTime` says “this judgment last changed value.” Neither says “I successfully observed AWS/OpenStack 20 seconds ago.” The standardized Condition deliberately omitted a heartbeat field because continuously updating it caused write amplification at scale. ([GitHub](https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/1623-standardize-conditions/README.md?utm_source=chatgpt.com))

That makes stale external observation an explicit design problem. Cluster API provides a particularly concrete extension: its newer status design maintains a remote-connection probe and says node-dependent conditions should become `Unknown` after the last successful remote probe plus a grace period. It even keeps the probe timestamp itself out of the public API to avoid continuous reconciliation writes. ([GitHub](https://github.com/kubernetes-sigs/cluster-api/blob/main/docs/proposals/20240916-improve-status-in-CAPI-resources.md))

### The strongest criticism of “just use Conditions” comes from a Conditions-heavy project

Cluster API is an unusually useful longitudinal case because it tried a strong version of the pattern and then revised it. Its 2020 Conditions proposal wanted an at-a-glance view over a hierarchy of infrastructure objects and was explicitly designed so providers could add and change their own condition sets. That proposal has since been marked superseded. ([GitHub](https://github.com/kubernetes-sigs/cluster-api/blob/main/docs/proposals/20200506-conditions.md?utm_source=chatgpt.com))

The replacement says the earlier model imposed very strict requirements: essentially every resource got `Ready`, with `Ready` summarizing the other conditions. Maintainers concluded that this “one fits all” rule had significant limitations. A higher-level deployment-like object can be operational while deliberately tolerating unavailable members during rollout, so a literal “everything Ready” summary is not necessarily the useful question. The newer design narrows the semantic of Machine `Ready`, removes `Ready` from some higher-level abstractions, and introduces `Available` where tolerated disruption is part of the contract. ([GitHub](https://github.com/kubernetes-sigs/cluster-api/blob/main/docs/proposals/20240916-improve-status-in-CAPI-resources.md?utm_source=chatgpt.com))

It also makes roll-up membership explicit and extensible. For example, Cluster `Available` has a defined set of required conditions plus `availabilityGates`; third-party conditions only affect availability when explicitly admitted as gates. ([GitHub](https://github.com/kubernetes-sigs/cluster-api/blob/main/docs/proposals/20240916-improve-status-in-CAPI-resources.md)) That addresses one subtle compatibility problem with an automatically aggregated condition list: merely adding a diagnostic condition should not unexpectedly change the old meaning of “healthy”.

Cluster API supplies another useful criticism of Kubernetes orthodoxy. Kubernetes API conventions deprecate phase-style state-machine fields because adding enum values is difficult for compatibility and because conditions expose independent properties more directly. ([GitHub](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/.agents/skills/k8s-api-conventions/references/api-conventions.md)) Yet Cluster API explicitly decided to **retain its `phase` fields**, saying maintainers had consensus that they still provided valuable user information. ([GitHub](https://github.com/kubernetes-sigs/cluster-api/blob/main/docs/proposals/20240916-improve-status-in-CAPI-resources.md)) In other words, even a project moving toward standard `metav1.Condition` did not conclude that conditions should replace every simpler lifecycle summary.

### Nova and Neutron made almost opposite choices

Nova's public model is intentionally lifecycle-centric. A server has a compact status such as `BUILD`, `ACTIVE`, `ERROR`, `MIGRATING`, or `SHUTOFF`, calculated from internal VM and task state. ([OpenStack Docs](https://docs.openstack.org/api-guide/compute/server_concepts.html?utm_source=chatgpt.com)) It does not attempt to turn the health of every Neutron attachment, credential, volume, or other OpenStack object into one giant server condition set. That makes the server state comparatively understandable, but it also means “ACTIVE” is not “all associated resources agree with reality.”

Its stale-state behavior exposes that boundary clearly. A lost compute service can leave a server recorded as `ACTIVE`, because the observer that would update it is gone. Nova's newer down-cell API behavior solves a different case—failure to obtain the record from a portion of Nova's own database/service topology—by returning partial data with `UNKNOWN`. ([OpenStack Docs](https://docs.openstack.org/?utm_source=chatgpt.com)) Thus “observer unreachable” is not uniformly folded into server lifecycle status.

Neutron encountered a closer version of the compound-resource problem. A port may require several asynchronous actors to finish. Rather than expose `DHCPReady`, `L2WiringReady`, `SecurityGroupsReady`, etc. as public Conditions, it deliberately kept the externally useful scalar `status` and introduced internal provisioning blocks. The design document starts from exactly this rationale: setting `ACTIVE` was easy with one provisioner; multiple asynchronous provisioners made the transition unsafe; therefore each required entity acquires a block and `ACTIVE` is only set after all blocks clear. ([OpenStack Docs](https://docs.openstack.org/neutron/10.0.0/devref/provisioning_blocks.html?utm_source=chatgpt.com))

That is a notable “simpler status preferred” case: complexity lives behind an explicit completion barrier instead of in the public state vocabulary. Neutron has nevertheless added orthogonal public dimensions when their semantics really differ; `data_plane_status` is explicitly independent of the ordinary port `status` and is owned by outside entities rather than Neutron itself. ([OpenStack Docs](https://docs.openstack.org/api-ref/network/v2/?utm_source=chatgpt.com))

### EC2 uses fixed checks rather than arbitrary conditions

EC2's model is much closer to a health-check vector. Today the vector has system, instance, attached-EBS, and optional application components. AWS defines the top-level calculation straightforwardly: every applicable check must pass for overall `OK`; one or more failures makes it `impaired`. ([AWS Documentation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/monitoring-system-instance-status-check.html?utm_source=chatgpt.com)) Unlike generic Kubernetes Conditions, the check types and polarity are controlled by one API owner, so a generic conjunction is possible.

The other important feature is epistemic state. The check vocabulary contains `initializing` and `insufficient-data`, not merely healthy/unhealthy. AWS explicitly warns automation not to interpret missing status-check datapoints as failure. ([AWS Documentation](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_DescribeInstanceStatus.html?utm_source=chatgpt.com)) That keeps “we observed something bad” separate from “we do not currently have a trustworthy observation.”

Its evolution story is different from a condition-map API. AWS can add another named check family—as attached-EBS and application checks demonstrate—but an aggregate defined as “all applicable checks” changes its effective predicate as checks are added. Detailed consumers remain able to inspect the dimensions separately; consumers using only the aggregate intentionally inherit the broader definition.

### Juju's interesting choice is not to aggregate orthogonal facts

Juju's unit presentation is perhaps the clearest rejection of the premise that every object needs one status. A unit can be `active/lost`: the charm's last workload assessment can be “active” while the controller's assessment of its management agent is “lost”. Those facts answer different questions, so Juju retains both. ([Ubuntu Documentation](https://documentation.ubuntu.com/juju/3.6/reference/status/?utm_source=chatgpt.com))

Where it *does* aggregate, it uses a deliberately small severity/order vocabulary. Application status can be inferred from unit workloads, and the Ops framework lets individual charm components contribute statuses, selecting `blocked` ahead of `maintenance`, then `waiting`, then `active`. ([Canonical](https://canonical.com/juju/docs/ops/latest/_modules/ops/charm/?utm_source=chatgpt.com)) That is simpler than arbitrary Conditions because all inputs have the same known semantics and ordering.

The trade-off is correspondingly clear. Adding another component requires no schema migration, but once several component judgments are reduced to one `blocked` or `waiting`, the scalar alone no longer tells the consumer which independent provider part disagreed. Messages and other model details have to restore that information.

### Crossplane shows what an “all children ready” composite looks like

Crossplane is close to the VM-plus-addresses-plus-credential shape because a composite is expressly an object backed by a changing collection of independently reconciled child resources. It keeps two top-level questions distinct: `Synced` asks whether reconciliation itself succeeded; `Ready` asks whether the composition reports the required children ready. ([Crossplane Documentation](https://docs.crossplane.io/v2.2/composition/composite-resources/?utm_source=chatgpt.com))

Its readiness machinery also demonstrates the awkward edge of generic composition. Not every Kubernetes object has a useful `Ready=True` condition, so composition supports resource-specific readiness checks and even a `None` check for a child that should not gate readiness. ([Crossplane Documentation](https://docs.crossplane.io/v1.20/guides/function-patch-and-transform/?utm_source=chatgpt.com)) Thus the attractive rule “composite Ready iff every child Ready” rapidly becomes “every child satisfies its configured readiness predicate.” The set of children can grow freely, but the aggregation semantics still have to say which new children are gates.

### What the designs disagree about

The main fault lines are therefore more precise than “Conditions versus enum”.

**Identity of failure.** Kubernetes-style conditions preserve names such as `InfrastructureReady` or `CredentialValid`; Neutron's provisioning block preserves actor identity internally but not necessarily in its public scalar; Juju's priority roll-up and Nova's lifecycle status discard still more identity. Crossplane keeps child identity in the object graph while publishing only a small composite summary.

**Roll-up semantics.** EC2 can safely use an AND because its checks all share known positive polarity. Juju can use a priority because its status vocabulary has a defined ordering. Neutron can use “last block removed” because its blocks all mean “this required provisioning actor is unfinished.” Kubernetes cannot define any equivalent generic operation over Conditions, because arbitrary condition types do not share semantics. ([GitHub](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/.agents/skills/k8s-api-conventions/references/api-conventions.md))

**Freshness semantics.** Several systems separately model “bad”, “unknown”, and “old”. Kubernetes `observedGeneration` handles stale desired-state reconciliation; Cluster API adds explicit remote-observation expiry; EC2 has `insufficient-data`; Juju has agent `lost`; Neutron refuses to clear a provisioning obligation without positive completion. Nova demonstrates what happens when such freshness is outside the scalar lifecycle state: a machine can remain reported `ACTIVE` after its compute reporter disappears. ([GitHub](https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/1623-standardize-conditions/README.md?utm_source=chatgpt.com))

**Evolution.** Open condition names and child-resource sets make adding dimensions structurally easy, but they do not make changes to the *meaning of the summary* automatically backward-compatible. Conversely, small enums make semantics easy for consumers but are awkward to extend. Kubernetes explicitly cites enum evolution as a reason to move away from universal `phase` fields, while Cluster API's decision to retain phases shows that consumers sometimes value the stable coarse state enough to accept that limitation. ([GitHub](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/.agents/skills/k8s-api-conventions/references/api-conventions.md))

So the published systems do not converge on one canonical representation. They converge more strongly on one separation of concerns: **the observations that explain what is independently true are not necessarily the same abstraction as the compact status presented to a human or automation**, and “stale/unknown” is different again from “observed failure.” The substantial design disagreement is over which of those layers should be part of the public API, and how much information a roll-up is allowed to discard.
