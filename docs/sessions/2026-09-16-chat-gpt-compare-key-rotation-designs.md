A pattern is emerging already: “rotation” means three different things across these systems. Some put a key/version identifier in every ciphertext (Tink, Vault, optionally Rails); some deliberately do not and instead try a key list (Django, MultiFernet, Rails by default); and envelope-encryption formats such as the AWS Encryption SDK can carry *multiple* encrypted copies of a per-message data key, which changes the migration semantics substantially.

## Turn 4: ChatGPT

The strongest operational distinction is “selection by metadata” versus “trial decryption.” Metadata-bearing designs make retirement auditable: you can count remaining ciphertexts by key/version without touching plaintext. Trial-list designs are simpler to bolt onto an environment-variable key, but they make both latency and “are we done yet?” depend on an application-level sweep, token TTLs, or extra bookkeeping.

The systems you named fall into three broad families: **key-ID-in-ciphertext**, **try-a-list-of-keys**, and **envelope encryption with one or more wrapped data keys**. The distinction matters more operationally than the choice of AES library: it determines whether a rotation is observable, how a mixed-version fleet behaves, and whether “safe to delete” can be answered by inspecting stored data or only by attempting decryption.

### Tink: the clearest example of a staged distributed rotation

Tink is unusually explicit about the part that many “previous keys” examples omit. The project says there is almost never an atomic switch across all machines and ciphertexts. Its recommended lifecycle is therefore: add the new key as enabled but **not primary**, roll that keyset everywhere, and only when every binary knows the key promote it to primary. ([Google for Developers](https://developers.google.com/tink/design/keysets?utm_source=chatgpt.com))

That point explains why Tink deprecated APIs such as `rotate-keyset` that added and immediately promoted a key. The earlier convenience operation was precisely wrong for a rolling deployment: once one new instance encrypts with K2, an old instance carrying only K1 cannot decrypt that write. ([GitHub](https://github.com/tink-crypto/tink/blob/master/java_src/src/main/java/com/google/crypto/tink/integration/android/AndroidKeysetManager.java?utm_source=chatgpt.com))

The key-ID prefix also turns retirement into a measurable database migration when Tink prefixes are used. It is important, though, that Tink explicitly says the prefix is unauthenticated. A program must not treat “ID 1234” as authorization to use some key without subsequently authenticating the AEAD ciphertext. ([Google for Developers](https://developers.google.com/tink/wire-format?hl=en&utm_source=chatgpt.com))

### AWS Encryption SDK: rotation by wrapping data keys rather than fields directly

This is structurally different from replacing an AES-GCM field key. Each message gets a unique data key; the configured Raw AES key protects that data key. The ciphertext message therefore contains the encrypted field plus one or more **encrypted data keys**. The AWS Encryption SDK itself does not require an AWS account, and Raw AES keyrings exist specifically for caller-supplied AES wrapping keys, although AWS recommends stronger durable protection for those wrapping keys than an ordinary process secret when available. ([AWS Documentation](https://docs.aws.amazon.com/encryption-sdk/latest/developer-guide/introduction.html?utm_source=chatgpt.com))

There are two interesting overlap strategies. A service can encrypt new values only with K2 while using a decrypt-only multi-keyring containing K2 and K1. That resembles Rails/Tink. Alternatively it can encrypt each data key under both K2 and K1; then either wrapping key can decrypt that message. ([AWS Documentation](https://docs.aws.amazon.com/encryption-sdk/latest/developer-guide/faq.html?utm_source=chatgpt.com)) The latter reduces availability coupling but also means that, during the overlap, possession of the old key still opens newly created data. That distinction matters especially when rotation is responding to suspected compromise rather than routine hygiene.

AWS's own migration history is a warning against treating the ciphertext format as incidental. The move to key commitment required staged compatibility policies; turning on new-format encryption before all readers understood it could make rollback impossible without rewriting ciphertexts. ([AWS Documentation](https://docs.aws.amazon.com/encryption-sdk/latest/developer-guide/migration-guide.html?utm_source=chatgpt.com))

### Rails: close to the environment-variable model, with an optional escape from trial decryption

Rails' standard rotation mechanism is perhaps the most direct analogue to “an env var becomes a list of env vars.” A key provider accepts several keys; current Rails uses the **last** one for new encryption and can try all of them for decryption. ([Ruby on Rails Guides](https://guides.rubyonrails.org/active_record_encryption.html?utm_source=chatgpt.com))

There is an interesting documentation discrepancy. The Rails 7.1.5.2 API prose said `encryption_key` returned the **first** key, while the source code directly underneath used `@keys.last`. Current Rails 8.1 API documentation and the guide say **last**, agreeing with the implementation. ([Ruby on Rails API](https://api.rubyonrails.org/v7.1.5.2/classes/ActiveRecord/Encryption/KeyProvider.html?utm_source=chatgpt.com))

`store_key_references` converts the scheme from “try all keys” into “select by header.” Rails' key reference is quite short: `Key#id` is only four hex characters of SHA-1 of the secret. ([Ruby on Rails API](https://api.rubyonrails.org/classes/ActiveRecord/Encryption/Key.html?utm_source=chatgpt.com)) That is an addressing hint rather than a cryptographic identity, much like Tink's prefix. Authentication still comes from AES-GCM.

Rails also demonstrates that key rotation is not the only compatibility axis. Its 7.0→7.1 digest changes produced reports where an upgraded application could read some old data but rollback could no longer read ciphertext newly created by the upgraded version. Rails added compatibility settings specifically around those digest changes. ([GitHub](https://github.com/rails/rails/blob/main/guides/source/upgrading_ruby_on_rails.md?utm_source=chatgpt.com))

### Django: useful rotation semantics, but not the same encryption problem

Django's built-in mechanism is worth studying mainly because it is a clean example of **fallback validation without ciphertext key IDs**. The new `SECRET_KEY` is used to create new signatures; `SECRET_KEY_FALLBACKS` permits old signatures, sessions and password-reset tokens to remain valid temporarily. Django explicitly warns that fallback verification costs increase with the number of keys. ([Django Project](https://docs.djangoproject.com/en/6.1/ref/settings/?utm_source=chatgpt.com))

Its most instructive criticism is the rolling-deployment ticket. A user pointed out that changing the primary secret and fallbacks in one deployment can produce:

old instance → signs K1  
new instance → signs K2  
old instance → cannot validate K2.

The proposed correction was two phases: distribute knowledge of K2 everywhere while still signing K1, then switch the primary. Django closed the ticket as invalid because its documentation does not generally try to cover distributed deployment considerations; the response did not claim that mixed fleets somehow avoid the described problem. ([Django](https://code.djangoproject.com/ticket/35400)) Tink, by contrast, has made essentially that two-phase rule part of its formal rotation documentation.

For actual encrypted Django model fields, a third-party package such as `django-fernet-encrypted-fields` applies a similar previous-key idea and explicitly says existing records can be re-encrypted by loading and saving them. ([GitHub](https://github.com/jazzband/django-fernet-encrypted-fields?utm_source=chatgpt.com))

### Vault Transit: the strongest built-in migration lifecycle

Vault makes the ciphertext's key version overt: `vault:v17:...`. The service owns the entire historical keyring, so callers never send the raw AES key alongside their process configuration. A rotation only changes which version new encrypt operations use; all allowed historical versions remain readable. ([HashiCorp Developer](https://developer.hashicorp.com/vault/tutorials/encryption-as-a-service/eaas-transit?utm_source=chatgpt.com))

`rewrap` is the notable feature. An application or batch worker can submit an old ciphertext and receive one under the latest key without ever receiving the plaintext. HashiCorp explicitly suggests that this can happen slowly in a background process to control database load. ([HashiCorp Developer](https://developer.hashicorp.com/vault/tutorials/encryption-as-a-service/eaas-transit-rewrap?utm_source=chatgpt.com))

It also separates **“stop ordinary decryption”** from **“destroy the key.”** Raising `min_decryption_version` archives older versions outside the working set and rejects their ciphertexts, but administrators can lower that threshold again if necessary. That is a safer retirement test than immediately deleting K1. ([HashiCorp Developer](https://developer.hashicorp.com/vault/docs/secrets/transit?utm_source=chatgpt.com))

The downside of putting all versions into a managed key object is that key history itself becomes state that has to scale. Vault has both an old real-world performance report involving extremely frequent rotations and current documentation warning that the archived version structure can grow beyond some storage backends' limits. ([GitHub](https://github.com/hashicorp/vault/issues/925?utm_source=chatgpt.com))

### libsodium: the primitives deliberately leave this protocol to you

A libsodium construction often looks deceptively simple because the AEAD API itself has no concept of K1 versus K2. The library expects the protocol/application to store what it requires alongside the ciphertext, particularly the nonce. ([GitHub](https://github.com/jedisct1/libsodium-doc/blob/master/quickstart/README.md?utm_source=chatgpt.com)) A robust application may therefore invent a record format with a format version and key identifier, but that format is the application's protocol, not “the libsodium format.”

`crypto_secretstream`'s references to automatic key rotation can be misleading in this context. Its rekeying changes the running state of **one ordered encrypted stream**; it does not mean that calling libsodium somehow manages historical database master keys. ([GitHub](https://github.com/jedisct1/libsodium-doc/blob/master/secret-key_cryptography/secretstream.md?utm_source=chatgpt.com))

This is also where nonce management and master-key rotation can become conflated. Sodium warns that constructions with short nonces require more application-level coordination and rotation and describes this as tricky; it generally encourages longer-nonce constructions where possible. ([GitHub](https://github.com/jedisct1/libsodium-doc/blob/master/secret-key_cryptography/encrypted-messages.md?utm_source=chatgpt.com))

### MultiFernet and Laravel: the simple fallback-list pattern

Both expose the basic pattern many applications independently invent: a distinguished current key plus an ordered sequence of previous keys, with trial authentication/decryption.

`MultiFernet` adds one particularly useful operation: `rotate(token)`, which returns a token under the current key while retaining the original timestamp. But it has no idea which tokens exist in a database, so scheduling and completeness remain an application concern. ([Cryptography](https://cryptography.io/en/48.0.1/fernet/?utm_source=chatgpt.com))

Laravel 11 made essentially the same policy first-class in environment configuration: `APP_KEY` plus `APP_PREVIOUS_KEYS`. New data uses `APP_KEY`; old keys are attempted only during decryption. ([Laravel](https://laravel.com/framework/docs/12.x/encryption?utm_source=chatgpt.com)) This is operationally simple, but the absence of a key identifier is exactly why the operator cannot distinguish “old-key ciphertext remains” from “this key is no longer needed” without TTL knowledge, a full migration, or separate metadata.

### ASP.NET Core: treating the key ring itself as durable infrastructure

ASP.NET Core's Data Protection system represents the other extreme from an environment-variable list. Every ciphertext says exactly which GUID-labelled key produced it, while the shared repository stores key lifecycle metadata. It even creates replacement keys with a default **two-day activation delay** so other machines get time to observe the new key before it starts encrypting. ([Microsoft Learn](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-management?view=aspnetcore-10.0&utm_source=chatgpt.com))

Microsoft's advice about deletion is revealing: it generally says don't. Expired keys stop being used for new protection but remain available for old data; removing them makes matching payloads permanently inaccessible. ([Microsoft Learn](https://learn.microsoft.com/ga-ie/aspnet/core/security/data-protection/configuration/default-settings?view=aspnetcore-8.0&utm_source=chatgpt.com)) This is appropriate for a subsystem that often has no knowledge of whether its caller used `Protect` for a 20-minute cookie or a secret intended to live for ten years.

Its operational history also shows the cost of the shared-key-ring approach. A key repository that is ephemeral, incorrectly shared, temporarily unreadable, or stale can turn an otherwise routine rotation into cross-node authentication failures. Those cases show up repeatedly in ASP.NET Core issue reports. ([GitHub](https://github.com/dotnet/aspnetcore/issues/28475?utm_source=chatgpt.com))

### What is surprisingly consistent across them

Almost none of these systems make **“decrypt old ciphertext and silently write a replacement during an ordinary read”** the universal default. Tink and AWS leave migration to the application; Rails reads old schemes without mutating them; Vault provides an explicit rewrap operation; MultiFernet exposes an explicit rotate operation; Laravel only supplies fallback decryption; ASP.NET keeps historical keys rather than rewriting arbitrary caller data. Vault is the closest to making background re-encryption a first-class managed operation.

There is also a recurring deployment rule independent of library: **a reader must learn K2 before any writer can emit K2**. Tink says this explicitly. The Django multi-node ticket independently arrives at the same conclusion. ASP.NET's two-day activation delay automates a variant of it. ([Google for Developers](https://developers.google.com/tink/design/keysets?utm_source=chatgpt.com))

Finally, “safe to remove” has two meanings that systems often blur. Removing K1 from the **active application's read set** may be safe once no live production ciphertext requires it. Actually **destroying K1** is stronger: backups, delayed queues, snapshots, disaster-recovery restores, rarely accessed rows and exported ciphertext can still depend on it. Vault therefore has `min_decryption_version` before destruction; Tink can disable keys before deletion; ASP.NET explicitly discourages deletion. ([HashiCorp Developer](https://developer.hashicorp.com/vault/docs/secrets/transit?utm_source=chatgpt.com))

So the survey does not point to one universal design. The main documented choices are whether key identity is encoded in each ciphertext, whether compatibility is represented as a key list or a managed keyring, whether re-encryption is explicit or expiry-based, and whether retirement is a reversible policy change or irreversible key destruction. The systems above make different choices on each axis, and their real-world failures largely occur when one of those distinctions is hidden from operators.
