# Compare concurrency testing methods

Source: https://chatgpt.com/share/6aa92d9e-0fdc-83ed-a8a5-956a00600e7c

---

**User**

Context: A control plane records intent, then a worker performs provider calls and records the outcome. Runs can overlap, responses can be lost, and a late result can arrive after the work it belonged to was replaced. Defects here are rare in normal use and severe when they occur.

Question: How do teams find defects in concurrent workflows and state machines, and what does each method actually catch?

Cover: deterministic simulation testing; property based and model based testing; fault and latency injection; chaos testing; formal specification such as TLA+ or Alloy; randomized interleaving tools; idempotency and replay testing; and plain example based tests of specific interleavings.

For each: the class of defect it finds, the effort to adopt, what it demands of the code under test, how the result is reproduced when it fails, and the reported experience of teams who used it, including those who abandoned it.

Give named cases where one of these found a real bug that other methods missed.

Evidence rules: cite engineering write-ups, papers and repositories with dates. Separate what a method guarantees from what a team reports anecdotally.

**ChatGPT**

One important distinction is emerging from the evidence: “chaos” and “fault injection” are not synonyms in practice. Fault/latency injection is often a test-harness technique with an oracle; chaos programs are usually broader operational experiments whose strength is validating real dependencies and recovery behavior, but whose oracle is often weaker.

---

**ChatGPT**

The methods are complementary because they search different spaces. For the workflow you describe, the dangerous state is not merely “two things ran concurrently”; it is that **an operation that was once legitimate loses authority while it is in flight, yet its later response is still accepted**. That requires testing ordering, failure semantics, and the state-machine invariant that decides which result is still entitled to mutate current state.

A useful way to read the techniques below is:

- **formal methods** search an abstract design;
- **deterministic simulation and controlled schedulers** search executions of implementation code;
- **property/model-based testing** searches operation sequences and supplies an oracle;
- **fault injection** searches failure semantics;
- **chaos** asks whether the assembled real system behaves as expected;
- **idempotency/replay tests** attack retry and recovery semantics;
- **handwritten interleavings** permanently pin down known hazards.

Effort ratings below are my estimate for retrofitting an existing asynchronous service, rather than claims made by the cited teams.

## The most informative cases where one technique found what another had missed

**DynamoDB/TLA+, 2015** is probably the clearest design-level example. The data-loss error required a shortest counterexample of 35 high-level steps. It had already survived extensive design review, code review and testing. This is almost the archetype for “rare in ordinary use, catastrophic if reached.” ([Leslie Lamport's Home Page](https://lamport.azurewebsites.net/tla/amazon-excerpt.html))

**Microsoft CHESS, OSDI 2008** is the clearest implementation-scheduling example. Ordinary stress testing had seen the defect only once in months; CHESS systematically controlled scheduling and found it in seconds, then made it immediately reproducible. ([Usenix](https://www.usenix.org/event/osdi08/tech/full_papers/musuvathi/musuvathi_html/index.html?utm_source=chatgpt.com))

**Riak Poolboy/QuickCheck, January 2012** is a good example of semantic state-space exploration beating coverage. The code already had 85% unit coverage, yet state-machine generation produced a five-step timeout sequence that leaked a worker, plus several EXIT/death bookkeeping defects. None caused the existing unit suite to fail. ([Riak](https://riak.com/posts/technical/quickchecking-poolboy-for-fun-and-profit/index.html))

**MongoDB Mobile/TLA+-generated tests, experiment in 2020, retrospective June 2025** is unusually useful because MongoDB has comparison numbers. Faithfully translating roughly 1,000 lines/21 merge rules into TLA+ exposed an actual infinite-recursion bug involving one participant swapping array elements while another moved one. The finite model then generated 4,913 behaviors and reached 100% branch coverage, against 21% handwritten and 92% from millions of AFL executions. ([MongoDB](https://www.mongodb.com/company/blog/engineering/conformance-checking-at-mongodb-testing-our-code-matches-our-tla-specs))

**TigerBeetle/Jepsen, reported June 2025** shows the reverse lesson: even extremely serious deterministic fuzzing can have a workload blind spot. Jepsen found a query-engine correctness error in a component covered by four fuzzers, including TigerBeetle's deterministic VOPR. The generator had accidentally arranged records so the problematic multi-index “probing” situation never arose. After replacing the constrained workload with arbitrary inputs plus a richer reference model, TigerBeetle's deterministic test trivially reproduced the bug. That is a particularly good demonstration that a powerful exploration engine cannot compensate for an impoverished generator or oracle. ([TigerBeetle](https://tigerbeetle.com/blog/2025-06-06-fuzzer-blind-spots-meet-jepsen/))

There is an analogous lesson inside **TigerBeetle's own DST**. In July 2023 it split its simulator into safety and liveness modes because temporary faults would eventually heal and conceal permanent-livelock situations. The new mode exposed a “resonance” bug in which repair requests alternated between precisely the replicas that lacked the requested log entries, forever. Their earlier safety-mode simulation would eventually reset the condition and miss it. ([TigerBeetle](https://tigerbeetle.com/blog/2023-07-06-simulation-testing-for-liveness/?utm_source=chatgpt.com))

## What matters specifically for your control-plane pattern

The key is to distinguish **deduplication** from **authority**.

Suppose intent generation 41 creates run A. A asks the provider to mutate something. The provider performs the mutation but its response is delayed. The control plane then records generation 42 and starts run B. B completes correctly. Finally A's response arrives.

An idempotency key prevents **A being executed twice**. It does not prevent **A from being accepted after B**. Those are different correctness properties.

The core safety invariant should be something close to:

> A worker outcome may update the current projection only while the intent/run generation that authorized the work is still current.

Operationally, that generally means each run carries an immutable **intent generation / fencing token**, and the outcome write is conditional on ownership still matching—for example conceptually, “update current state where generation = 41.” Once generation 42 exists, A's update affects zero rows. A may still be recorded as an historical or obsolete outcome, but it must not become current.

A second invariant is monotonicity: **a visible current generation can never decrease**, regardless of completion order.

A third belongs at the provider boundary: all retries of one logical provider mutation use the **same provider idempotency key**, while a genuinely new intent gets a new key. That handles the “provider committed but response was lost” ambiguity described by both Stripe and AWS. ([Stripe](https://stripe.com/blog/idempotency?utm_source=chatgpt.com))

The fourth is subtler: cancellation does not revoke causality. Once a provider request has escaped your process, “cancelled” should normally mean “we no longer wait for it,” not “we know it did not happen.” A later provider observation/callback can therefore be valid historical evidence without being authorized to overwrite the current generation.

## The test stack I would use here

I would not start by building a FoundationDB-scale simulator. For this particular architecture, the highest return is a layered approach:

1. **Write the state-machine invariants first**, preferably in a small TLA+ model. Model `record intent`, `start run`, `send provider request`, `provider commits`, `lose/delay reply`, `replace intent`, `retry`, `receive reply`, and `record result`. This is cheap enough to explore whether your generation/fencing rules are logically sufficient before spending heavily on implementation machinery. AWS's experience is strong evidence for this kind of design problem, while the MongoDB experience is a warning not to make the spec implementation-shaped or commit immediately to expensive trace conformance. ([Leslie Lamport's Home Page](https://lamport.azurewebsites.net/tla/amazon-excerpt.html))

2. **Turn every known dangerous sequence into a barrier-controlled ordinary test.** One essential regression is: A/provider effect occurs → withhold A reply → replace with B → complete B → release A → assert A cannot change current state. Repeat with A's reply lost and retried, duplicated, and delivered before/after each durable state transition. Thread Weaver's principle—explicit control points rather than sleeps—is the right shape. ([Google Open Source Blog](https://opensource.googleblog.com/2009/10/testing-race-conditions-in-java.html?utm_source=chatgpt.com))

3. **Add model/property-based sequence generation around the real state machine.** Commands should include create/replace intent, lease/start, timeout, provider success/failure/ambiguous success, retry, worker crash, duplicate delivery and result arrival. Shrinking makes the failures practical to debug. The Poolboy results illustrate why this finds mistakes that coverage-oriented unit testing does not. ([Riak](https://riak.com/posts/technical/quickchecking-poolboy-for-fun-and-profit/index.html))

4. **Make the fake provider fault-capable at semantic boundaries.** Especially support “perform effect but never return the response” and “perform effect, hold response until released.” Generic random HTTP latency is much less useful. Jepsen and Netflix's results show the value of deliberately exploring failure semantics rather than merely load. ([InfoQ](https://www.infoq.com/news/2016/03/failure-testing-netflix/?utm_source=chatgpt.com))

5. **Use a controlled/randomized scheduler if your important race is inside one worker/control-plane process.** If most nondeterminism is in queues/provider responses rather than threads, model those as scheduler events. Save the exact schedule. CHESS/PCT show why scheduler control is dramatically better than “run the test 100,000 times and hope.” ([Microsoft](https://www.microsoft.com/en-us/research/publication/a-randomized-scheduler-with-probabilistic-guarantees-of-finding-bugs/?lang=ja&utm_source=chatgpt.com))

6. **Continuously test idempotency and workflow replay separately.** Idempotency tests should deliberately lose replies after provider commitment and verify retries do not duplicate effects. If you have durable workflow histories, replay old production/test histories through new orchestration code in CI. But keep a separate fencing assertion, because idempotency alone does not provide newest-intent-wins semantics. ([Amazon Web Services, Inc.](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/?utm_source=chatgpt.com))

7. **Use chaos later, as a reality check rather than the primary race detector.** Once the invariants above are exercised deterministically, chaos is excellent for discovering that your real queue has different delivery behavior, your timeout is wrongly configured, a failover path does not work, or a dependency you thought was redundant is not. It is a poor first instrument for finding a five-event stale-result sequence because a failure is harder to reproduce and the oracle usually sees less internal state.

The evidence does not support a single “best” technique. It supports **cross-checking different search spaces**. FoundationDB and TigerBeetle are perhaps the strongest advocates of deterministic simulation, yet TigerBeetle explicitly added real-system nondeterministic testing, and Jepsen subsequently found a correctness bug its deterministic fuzzers had projected out of their generated state space. ([TigerBeetle](https://tigerbeetle.com/blog/2025-02-13-a-descent-into-the-vortex/?utm_source=chatgpt.com)) Likewise, AWS's TLA+ work found errors testing had missed, but AWS explicitly did **not** claim that checking the specification proved the implementation. ([Leslie Lamport's Home Page](https://lamport.azurewebsites.net/tla/amazon-excerpt.html))

For the failure you described, the best discriminator is therefore: **TLA+/model checking for whether your ownership protocol is sound; model/property-based generation plus deterministic fault/schedule control for whether the implementation really preserves it; idempotency testing for ambiguous provider outcomes; and a few explicit interleaving tests as permanent regression locks.** Chaos comes after those, to show that your abstraction of the real deployment was not wishful thinking.
