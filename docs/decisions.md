# Decisions

Only choices that the code does not explain. Rewrite an entry when it changes; git keeps the history.

Node runs Next.js; Bun only installs, runs scripts, and tests. Next.js on Bun has open runtime issues.

The Content Security Policy is static in next.config.ts. Clerk's generated policy allows scripts from any host unless nonces make every page dynamic.

The header and the page fill the large viewport, so the footer is below the fold and every page scrolls. The scrollbar is then always present, and no `scrollbar-gutter` is reserved. A reserved gutter doubles the scrollbar padding that Clerk's modal adds when it locks scrolling, which moves the page sideways.

`/` is one page for everyone. Signed-in parts render in the browser inside fixed-size regions, so the page stays static. Each server gets its own protected page.

Clerk's prebuilt components do sign-in, sign-up, and the profile inside the app: `<SignIn />` on `/sign-in`, and `<UserButton />`, which opens `<UserProfile />`. They include CAPTCHA, legal consent, and reverification, which custom flows must build and maintain. There is no sign-up URL, so `<SignIn />` signs up new users in the same flow and shows no sign-up link. Sign-in is email code or Google, and sign-up is public. Passkeys and MFA need a paid plan.

Clerk keeps its prebuilt structure and behavior, while `--clerk-*` CSS variables and stable element classes refer to the semantic tokens and shared primitives. Clerk hard-codes round avatars, so element classes make them square. Clerk's primary color is the neutral primary, not the brand color, because Clerk also uses it for text links and selected items. The profile has one outer card border and one one-pixel divider; nested scroll areas own neither border. Its three layers are monotonic in both themes. In light mode, the selected tab is darkest, the sidebar is lighter, and the content is lightest. Dark mode reverses that order: the content is darkest, the sidebar is slightly lighter, and the selected tab is lightest. Clerk and site surfaces use borders without elevation shadows. Clerk form actions keep their context-sensitive primary or danger treatment through Clerk's `data-color`; a destructive ghost action uses the shared `dangerGhost` variant instead of becoming a filled danger action. Controls with one fixed role name the matching shared button or input primitive.

Clerk's component code loads from Clerk's CDN, not from the `@clerk/ui` package. The package pins that code but adds hundreds of dependencies, and clerk-js loads from the CDN anyway.

There are no usernames. An account is found by its email address, which every account already has and which the person sharing a server almost always knows, while a handle has to be asked for first and is a second name for the same person. Clerk has no page for a user, so nothing needs a handle in a URL; if public profiles ever exist, they can use names people choose then. A first and last name are optional at Clerk and are not used here yet.

Convex keeps a users table synced from Clerk, because users will see other users when servers are shared, and billing needs a local user. It is keyed by the Clerk user ID, not tokenIdentifier: the deployment trusts one issuer, and Clerk's webhooks and API know only that ID.

One function syncs a user from Clerk's current state. The Clerk webhook, the client, and hourly reconciliation all call it, because a webhook can arrive late, twice, out of order, or never, and reading Clerk's current state makes all four the same. Removing a user deletes every server they own, so it happens only on the strongest evidence Clerk gives: a direct read of that account saying it does not exist. A list that leaves an account out is not that evidence, so reconciliation checks each one it misses the same way the webhook does. An account that cannot be checked stays as it was, and reconciliation goes on to the rest and then fails, so one account never keeps the others from being checked. Reading every account Clerk holds and checking every account we hold are independent halves of that run: a deletion nobody delivered must not wait for a working list. "Does not exist" means Clerk's own code for it, never the bare status, and before any removal the two sides must publish a signing key in common, because a secret key belonging to another Clerk instance answers that way for every account we hold and would otherwise delete every server on the deployment. An event that says an account is gone while Clerk's own read still returns it is not accepted, because accepting it would be the last time Clerk mentions it. An account Clerk has already deleted can still be given a server by an ownership transfer, for as long as it takes that deletion to reach us; the server is then deleted with the rest of that account's servers.

Clerk's `id` is who an account is. The primary email address and the picture are both optional at Clerk and both can change, so each is kept exactly as Clerk sends it and is absent when Clerk sends nothing. Every account is kept. A grant is held against the user ID, and the address only finds somebody at the moment they are shared with, so an account without one cannot be found and needs no other rule; and because an address can move from one account to another, two accounts here can hold the same one until the older webhook arrives, which makes sharing by that address refuse rather than choose. This is the model OpenID Connect, Google and GitHub all document: a stable key for identity, and a name as a way to look it up.

Server ownership is stored on the server, separate from memberships. The owner has no membership and holds every permission. A membership gives another user reads and its checked permissions. Rename, power, member management, SSH management, and deletion have independent permissions; new memberships default to every permission the caller can grant. Delegates can grant only permissions they hold and cannot change or remove a member with broader permissions. Only the owner can transfer ownership, to an existing active member; that membership is removed, and the previous owner receives a membership with every permission. The owner cannot leave; deleting the owner's account requests durable server deletion. An operation completes if its requester had the permission when requesting it, even if that permission is removed while the operation runs. A server that is being deleted accepts no change except its own deletion.

Platform permissions do not restrict direct SSH or filesystem access. Membership removal does not remove native SSH authorizations. SSH entries have no required platform-member association.

An authorized key entry is an occurrence in one file revision, not a key fingerprint: the same key can appear twice with different options, and an edit names the line it changes. Option order is meaningful to OpenSSH, so edits preserve ordered options and every untouched byte. `sshd -T` reports the configuration on disk, not the settings of the running daemon, and `sshd -t` accepts entries that authentication later rejects, so neither validates an entry. An `expiry-time` value without a `Z` suffix uses the server's timezone, and a date without a time means midnight at the start of that date, so new values are written in UTC with `Z` and shown in both forms.

SSH files remain authoritative on the server. Explicit file updates compare observed bytes and metadata, coordinate cooperating writes, replace the file, and verify the result. This is not compare-and-swap against independent editors. An uncertain outcome must not trigger a blind retry or rollback. OpenSSH authentication and sessions retain their native behavior.

Each allocation has a separate backend management key. Its private key is encrypted with an allocation-bound AES-GCM envelope. Cloud-init receives only its public key and a short-lived host key registration token. The server generates its host key locally; authenticated registration pins the public key without trusting the first SSH response. A repeated report can confirm the same key but never replace it; a different key is refused and recorded as a conflict, because it means either a copied bootstrap token or a replaced server. The report URL must be HTTPS, because the token travels in the request body. Both Primary IP addresses are recorded before the server boots, and a report is refused unless it comes from one of them: the proxy in front of the deployment replaces a client's own forwarding headers, and a request that carries its own address header is rejected before it arrives, so a copied token is useless from anywhere else. A server reports over IPv4 or from anywhere inside its IPv6 network. The bootstrap window is 15 minutes, because cloud-init reports within a minute. A member with the SSH permission can renew that window when the server no longer accepts Composery: the panel gives them one program to run on the server, which asks the SSH server for its own key file, host key and port, installs a new management key, removes the one Composery held before, and reports what it found. The new key pair stays pending until that report arrives, so a renewal nobody runs leaves access exactly as it was, and a lost or stale key is replaced rather than kept. Only inside that window may a report replace a pinned host key, and only from the server's own addresses; both conditions, never one. A customer who can no longer reach the server at all is a support case, not a panel feature. Deletion removes the stored secrets after infrastructure cleanup. Host-key registration and provider running state do not establish SSH reachability.

Server names are permanently claimed by one server identity. A server can rename back to its own historical name; other servers cannot claim it, even after deletion. Every claim stays in serverNames, and an old name resolves to the current one. The name follows DNS label rules because it may become a subdomain. The reserved list in convex/servers/reserved_names.ts is deliberately large, and a reserved name is reported as taken.

Rate limits exist to protect the system, not to slow people down: an account may have one server or hundreds. Limits are per user; a global limit would let one attacker block everyone. Expected failures such as a taken name are returned instead of thrown, because a thrown error rolls back the rate limit attempt it counted.

Quotas limit how many servers one user owns and how many the whole deployment holds. Both are counted from the create request until the provider confirms that the infrastructure is absent, and the owner's quota follows an ownership transfer. A missing quota row means a limit of zero, so a deployment creates nothing until an admin sets both. An admin sets quotas today and billing sets the user quota later. The deployment quota stays at or below the Hetzner project's server limit, which the API does not report; Hetzner allows two Primary IPs for each server in that limit and every server uses exactly two, so a separate address quota would only repeat the server quota. Rate limits are separate: they limit how often an account acts, not how much it holds.

Provider API pacing is separate from user admission. Cleanup has reserved worker capacity and API allowance.

The server identity is independent of its allocation backend and provider name. Hetzner resources use an opaque controller identifier, allocation identifier, and resource kind for ownership checks. Human-readable infrastructure names contain no project or deployment name. New allocations resolve the current configuration; existing allocations retain theirs.

Where an allocation is in its life and what is wrong with it are two separate things. The status says only creating, running, stopped, deleting or deleted; each part of it, the server, its addresses and the rules in front of it, says whether it was last seen as it should be, gone, or different from what was recorded, and one field says what the last attempt ran into. One word for all of that made a part being wrong stop everything: rules an admin took off in the provider's console stopped power commands that had nothing to do with them. A server of another type or in another place is the one difference that stops the rest, because it is not the server this allocation recorded.

What a failure means decides what happens next, and how often it has happened decides only how long the wait is. A failure is passing, waiting on something outside, invalid until its configuration changes, of an outcome nobody knows, or our own defect; each has its own schedule, from ten seconds to an hour. Repetition never turns one kind into another, and nothing is ever given up on: an allocation that is stuck says so and is still picked up again, because a customer's server that nobody comes back to is worse than one request an hour. The single exception is an operation whose own deadline has passed, which is over rather than waiting. A request whose outcome nobody knows is the one that is never sent again; the resource is looked for instead, which its own recorded state decides rather than the failure.

A Hetzner create request is recorded as uncertain before it is sent, so a lost response is resolved by looking the resource up, never by sending the request again. Each worker run takes an epoch and a lease; the lease fences database writes, not requests already sent. A result may change its operation's status only while that operation is still the allocation's current one, so a late result cannot finish or block the operation that replaced it. An admin retry takes a new epoch, so an outstanding run cannot undo it. Both Primary IPs are created before the server and deleted after it, and quotas are released only after Hetzner confirms that every owned resource is absent. Inventory scans record unknown resources as findings for an admin and never delete them. Start, graceful stop, and forced stop are separate operations; a graceful stop never becomes a forced one.

An allocation that has settled is never asked about on its own. One look at one server takes a claim from the deployment's hourly allowance, which is eight of its two thousand, and two requests of Hetzner's, so looking at each of them every five minutes runs out of our own allowance at about twenty servers and out of a project's 3600 an hour at about a hundred and fifty. The inventory scan already reads every server this controller labelled, fifty to a request, so what it sees is written into each allocation instead, and an allocation is woken only when there is work to do. One page every ten seconds costs the same whatever the fleet is, and how long a cycle takes is how old an observation can be, so the scan never stops walking: the last page of a cycle is followed by the first page of the next. The scan writes down only what it saw. An operation belongs to whoever holds the lease, and an allocation that is stuck stays stuck, because seeing the server is no answer to what the work ran into. What one look at a server means is worked out in one place, so the scan and the worker cannot come to different answers about the same server.

The work and cleanup queues have separate hourly allowances so neither starves the other, and cleanup's is no smaller than work's. Taking an allocation apart costs more claims than putting one together, and it is the path that gives a customer's addresses and quota back, so a burst too small to finish one deletion would hold both for minutes. A test that deleted two allocations at once is what showed it: the cleanup bucket could burst two claims, and the rest waited on a refill.

An allocation and the server it ran are removed in one change. Every way of reading an allocation starts from its server, so a server that had none, even between two mutations, would fail every read of it, including the cleanup that deletes the servers of a deleted account.

Each backend keeps its own state in its own table, with one row for each allocation, instead of fields or a nested object in `serverAllocations`. The worker changes its lease fields every few seconds, and a change to `serverAllocations` reruns every status query that reads it. A second backend adds its own table and one `backend` value, and changes no existing table. A backend's own error codes stay in its table, for admins; what everybody else reads is the shared lifecycle, what each part of the server looked like when it was last seen, and why the allocation is not moving.

Environment files live at the top of the repository, and each name says who reads it. `.env.local` is the app's, because Next reads only `.env`, `.env.local`, `.env.$(NODE_ENV)` and `.env.$(NODE_ENV).local`, and both `convex dev` and `clerk env pull` write that file. `.env.local.tests` is what a test run is given, by `bun run hetzner` and by nothing else: Bun reads `.env` and `.env.test` into every `bun test`, so a token in either would make the plain command create real servers, and `--env-file` replaces automatic loading, which is what makes one command the only way in. `.env.convex.example` is neither; it lists what a person puts into a deployment's own settings. A file inside the folder it serves was considered and refused: these are read from the directory a command was started in, and nothing looks upwards, so `tests/.env` would be ignored from the repository root and loaded the moment somebody's shell stood in `tests/`. `bun check` holds all three rules, because each mistake is silent.

Clerk's address is the same shape: `CLERK_API_URL` may replace it only when the deployment and the address both answer on this machine alone. A test fills a fake Clerk with accounts, and the webhook route re-reads the account from Clerk rather than trusting the event body, so without this a test would reach the real Clerk. Clerk's own SDK reads the fake's replies but does not check them, so what decides their shape is Clerk's published description, not the SDK.

Hetzner's address is a constant in `hetzner_cloud/api.ts`. `HCLOUD_FAKE_URL` may replace it only when both the deployment and the address answer on this machine alone, so a test can point the deployment at its own fake, and the same variable set on a real deployment changes nothing. A bootstrap report may travel over plain HTTP only to a loopback address, for the same reason: the token stays on the machine that sends it.

A Convex module path accepts only letters, digits, underscores, and periods: the backend refuses `hyphen-probe.js` on push. So Convex modules use snake_case with a directory-specific filename lint rule, and a test that mirrors one keeps its name. Every other file is kebab-case, because a Next.js route folder becomes a URL segment.

Server pages call `auth.protect()` themselves instead of matching routes in the proxy. Clerk deprecates `createRouteMatcher` in favor of checks at the resource.

All corners are sharp. The icon is a sharp square, so the site uses the same shape at every size. The Tailwind theme has no radius tokens.

Two typefaces give two voices. Chakra Petch (`font-brand`, or `font-wordmark` without the size adjustment, which the wordmark's measured metrics need) is for the logo, buttons, labels, and facts such as resource sizes: the places where the product acts or makes a promise. Onest (`font-sans`) is for everything people read, including headings. Chakra Petch alone feels distant to people who have never used a server, and Onest alone does not signal infrastructure. Chakra Petch is loaded at weight 500 only; Onest is variable, with body text at 350 and headings at 550.

Neutral colors use Tailwind palette tokens, not custom values. The page is stone-50 in light mode and stone-950 in dark mode. A surface is white in light mode. In dark mode, it is 25 percent of the distance from the page to stone-900, so the page and surface remain close but distinct in both themes. Interactive dark surfaces use stone-900 on hover and stone-800 while active. Static muted fills have their own token, so changing an interaction cannot change a badge or icon box. Each hover or active state is closer to the foreground than the state before it. Structural borders stay quiet. A control border moves one palette step for each interaction state, so a light secondary control does not jump from stone-200 to stone-400 on hover. Keyboard focus uses a one-pixel neutral outline for native and Clerk controls. Text inputs have no hover state and use a separate, stronger neutral border while focused. Brand and primary actions use perceptual state steps as large as danger actions. Danger actions use Tailwind red steps: a primary destructive action is filled, while a secondary destructive action starts as red text and gains a quiet red surface on interaction. Components use only semantic tokens, so a color changes in `globals.css` and nowhere else. The raw properties have an `--app-` prefix because embedded components can define generic properties such as `--border` on their own elements; a Tailwind semantic utility must not resolve through a property that another component can shadow.

Every internal link, including the logo, uses one `Link` that fades on hover with the same transition as buttons. An animated underline needs an always-present transparent underline, and Chrome paints it in the selection color when the text is selected.

Components join class names with clsx, not tailwind-merge. A `className` prop adds classes and never overrides the component's own. tailwind-merge does not read the Tailwind theme, so it must be configured by hand for every custom token, and a wrong configuration silently deletes classes, for example `font-body` (a weight) next to `font-sans` (a family).

The theme follows the operating system's light or dark preference. There is no manual toggle, so the server needs no stored preference and the first paint is correct.

SSH features need Linux, OpenSSH and Python 3, and they say so when a server lacks them instead of failing obscurely. Everything about the server that can be discovered is asked of the server, never assumed: which accounts exist, which key files apply, and what the SSH server's effective configuration is. What cannot be discovered is fixed by construction: cloud-init installs the management key for root, so Composery signs in as root on port 22, and it pins the Ed25519 host key that the server reports. The interpreters Composery runs are absolute paths, because a search path is attacker-controlled on a server whose owner has root. A customer who moves the SSH port, forbids root login, removes the Ed25519 host key, or replaces the operating system keeps a working server and loses the SSH features, visibly. The other features do not depend on any of this: power, deletion, quotas and status come from the provider's API.

A key edit names the revision of the file it was planned against, and the server's bytes must still match it. A stale revision is refused, which is also what makes a repeated request safe: the second attempt cannot apply twice, because the first one changed the file. An outcome that the server could not confirm is reported as uncertain and never retried on the caller's behalf.

Composery manages authorized key entries, and nothing else about SSH. It reads the SSH server configuration to learn which key files apply to an account, and never writes that configuration: a wrong setting there locks out every user, including Composery. One permission covers all key management, because anyone who can add a key can sign in and edit the same files by hand; a finer permission would promise a boundary that SSH does not enforce. Discovery states what it cannot know instead of guessing: a key command is a program and its keys cannot be listed, certificate sources are shown separately, and every answer comes from the configuration on disk, which the running daemon need not have reloaded. After an add or an update, Composery asks the running SSH server for the key's acceptance: the SSH protocol lets a client offer a public key without a signature, and the server either refuses it or asks for one, so the question needs no private key and opens no session. The server answers from Composery's address, so a key limited with `from=` is reported as unknown rather than refused, and a failed question never turns a successful write into an error.

SSH host certificates are not built. Pinning at creation protects Composery's own connections, and it is the customer, not Composery, who still meets a trust-on-first-use prompt. A host certificate would fix that, and would turn a legitimate host key change from an incident into a re-signing, but its principal is a name, so it needs the DNS scheme that the app feature will define, a certificate authority to hold and rotate, and a revocation list that reaches every server. Nothing built now is wasted: a certificate is one more line in the same file, and the pin stays valid beside it. Decide it with the app naming scheme, not before. `docs/ssh-certificates.md` holds the sketch and the evidence.

A system's published description of itself lives in `contracts/`, at the top of the repository rather than under `tests/`, because a contract checker is an oracle and an oracle that nothing proves is worse than none: it has to be right before anything can rely on it, which is what separates it from the harness. `scripts/contracts.ts` is the only thing that fetches a description, so a test never reaches the network and a change at a vendor arrives as a diff somebody reads rather than as a red build nobody asked for. The pinned file records the source, the day it was read, and a digest of the whole document; the subset is a declared list of operations, not a hand-cut file, so a reviewer can rerun it and read the difference.

Both halves of an exchange are checked: what Composery sends, and what a fake answers. For Hetzner both halves are ours, since we build the requests by hand. For Clerk the requests come from Clerk's own client, so checking them checks Clerk; what is worth checking there is everything we accept, because the client deserializes a reply without validating it and a fake could invent any field. The Clerk API version is the one that client asks for, and the fake refuses a request carrying another, so an upgrade cannot leave the pinned description behind quietly.

Where a system disagrees with its own description, running it wins and a waiver records the difference with its evidence. A waiver must be able to fail: it stops applying when the description at that place changes, it fails the run when its operation runs without the difference appearing, and each one carries a reproducer in `tests/contracts/`. Of the first two written, one was invented by analogy and the stale check removed it on its first real run.

`SSH_ACCESS_ENCRYPTION_KEYS` is an ordered list rather than one key, and every stored secret names the key that encrypted it in a version prefix that the encryption itself covers. Naming the key is what makes retirement a question the database answers instead of a guess: count what still names the old key. The alternative, trying each key in turn, is simpler and cannot answer it. The order is what expresses the two deployments a safe rotation needs, which two separate variables cannot: a key must be readable everywhere before anything seals with it, or a value written by one deployment cannot be opened by another. `ssh/secrets:reEncrypt` walks the stored values and leaves a row that changed while it ran, because a renewal writes the same fields and its secrets are newer.

A server type Hetzner no longer offers is permanent, like an image it no longer offers, and unlike capacity, which is the other thing a precondition failure at that point would mean. The three were the same status until a test could not tell them apart.

A deprecation Hetzner has announced does not make a thing unusable. Hetzner's `deprecation` carries the day it was announced and the day the thing stops working, and it announces months ahead; `status` is what says whether an image can be used now. Reading the announcement as "gone" would refuse every new server from the day Hetzner says a word about the image we pin, on a date Hetzner chooses. So an image is chosen on its status and on `unavailable_after` being in the future, and a location the same.

A server's addresses are shown, plainly and read-only. Everything a customer does next points at one: a DNS record, a connection string, another machine's allowlist, a reverse proxy's upstream, a monitoring target, and the `known_hosts` entry on every client that ever connected. The case that settles it is the first one: a server can always tell you its own addresses, and you cannot reach a server to ask without one. A name would replace that, and the two kinds of name are not alike. A name for a whole server is entirely outside the server, a record pointing at an address, so nothing the customer does inside can break it. A name for one app is not: routing several apps on one server by hostname needs something on the server doing the routing, which is state the customer can remove, so it degrades like the SSH features do and needs the same treatment. The reasoning is in [the session that worked it out](sessions/2026-09-14-claude-code-names-funnel-refactoring-and-repository-reorganization.md).

A session in `docs/sessions/` is input, not instruction, whether it informed research, implementation, or naming. `bun run session:import <source>` adds one as `<date>-<reader>-<title>.md`. A session keeps what the person and the assistant said to each other: their text, the questions the assistant asked through a prompt with their answers, and commands, interruptions, compactions, and continuations as session events. It leaves out tool calls and their output, thinking, and what the harness adds, by kind of record and never by judgement of content: git and the current documents hold what the work produced, and a session holds the reasoning between them. A Claude Code session follows its continuations back to the first, and follows the path of messages that Claude Code kept, so a rewound branch is not part of it. A conclusion that a session reaches belongs in the document for its topic.
