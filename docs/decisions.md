# Decisions

Only choices that the code does not explain. Rewrite an entry when it changes; git keeps the history.

Node runs Next.js; Bun only installs, runs scripts, and tests. Next.js on Bun has open runtime issues.

The Content Security Policy is static in next.config.ts. Clerk's generated policy allows scripts from any host unless nonces make every page dynamic.

The header and the page fill the large viewport, so the footer is below the fold and every page scrolls. The scrollbar is then always present, and no `scrollbar-gutter` is reserved. A reserved gutter doubles the scrollbar padding that Clerk's modal adds when it locks scrolling, which moves the page sideways.

`/` is one page for everyone. Signed-in parts render in the browser inside fixed-size regions, so the page stays static. Each server gets its own protected page.

Clerk's prebuilt components do sign-in, sign-up, and the profile inside the app: `<SignIn />` on `/sign-in`, and `<UserButton />`, which opens `<UserProfile />`. They include CAPTCHA, legal consent, and reverification, which custom flows must build and maintain. There is no sign-up URL, so `<SignIn />` signs up new users in the same flow and shows no sign-up link. Sign-in is email code or Google, and sign-up is public. Passkeys and MFA need a paid plan.

Clerk keeps its prebuilt structure and behavior, while `--clerk-*` CSS variables and stable element classes refer to the semantic tokens and shared primitives. A primitive is transposed only onto the same atomic Clerk element and state surface: a badge onto a badge span, a named text field onto an input, an OTP input style onto an OTP input, and a switch part onto the matching switch part. Clerk's polymorphic base `formFieldInput` is not mapped because the same slot reaches incompatible input types; a specific `FieldId` is mapped only when Clerk defines it as the same control. A menu, modal, field group, or panel does not receive a primitive's layout because it looks similar. When Clerk has an extra wrapper, the shared parent rule may address that wrapper so the visible result stays the same without copying component styles into the Clerk provider. Clerk's avatar elements use the site's rounded-square shape instead of Clerk's default circle. Clerk's primary color is the neutral primary, not the brand color, because Clerk also uses it for text links and selected items. The profile has one outer card border and one one-pixel divider; nested scroll areas own neither border. Its three layers are monotonic in both themes. In light mode, the selected tab is darkest, the sidebar is lighter, and the content is lightest. Dark mode reverses that order: the content is darkest, the sidebar is slightly lighter, and the selected tab is lightest. Clerk and site surfaces use borders without elevation shadows. Clerk form actions keep their context-sensitive primary or danger treatment through Clerk's `data-color`; a destructive ghost action uses the shared `dangerGhost` variant instead of becoming a filled danger action. Controls with one fixed role name the matching shared button or input primitive.

Shared button variants, badge variants, and the checked switch appearance are CSS utilities in `src/components/ui/variants.css`. Native primitives name them directly. `clerk.css` maps Clerk's `data-color` and `data-checked` attributes to those same utilities with `@apply`, so its adapter owns selectors but no second copy of the appearance. Shared fonts and colors remain semantic tokens. All CSS enters through `globals.css` so the layer order is explicit.

Clerk's component code loads from Clerk's CDN, not from the `@clerk/ui` package. The package pins that code but adds hundreds of dependencies, and clerk-js loads from the CDN anyway.

There are no usernames. An account is found by its email address, which every account already has and which the person sharing a server almost always knows, while a handle has to be asked for first and is a second name for the same person. Clerk has no page for a user, so nothing needs a handle in a URL; if public profiles ever exist, they can use names people choose then. A first and last name are optional at Clerk and are not used here yet.

Convex keeps a users table synced from Clerk, because users will see other users when servers are shared, and billing needs a local user. It is keyed by the Clerk user ID, not tokenIdentifier: the deployment trusts one issuer, and Clerk's webhooks and API know only that ID.

One function syncs a user from Clerk's current state. The Clerk webhook, the client, and hourly reconciliation all call it, because a webhook can arrive late, twice, out of order, or never, and reading Clerk's current state makes all four the same. An epoch is committed only when a read succeeds; a newer read that fails therefore does not discard an older successful result, while an older result cannot replace a newer one. Removing a user deletes every server they own, so it happens only on the strongest evidence Clerk gives: a direct read of that account saying it does not exist. A list that leaves an account out is not that evidence, so reconciliation checks each one it misses the same way the webhook does. An account that cannot be checked stays as it was, and reconciliation goes on to the rest and then fails, so one account never keeps the others from being checked. Reading every account Clerk holds and checking every account we hold are independent halves of that run: a deletion nobody delivered must not wait for a working list. "Does not exist" means Clerk's own code for it, never the bare status, and before any removal the two sides must publish a signing key in common, because a secret key belonging to another Clerk instance answers that way for every account we hold and would otherwise delete every server on the deployment. An event that says an account is gone while Clerk's own read still returns it is not accepted, because accepting it would be the last time Clerk mentions it. A removed Clerk ID stays blocked by a permanent local tombstone because Clerk IDs identify accounts for their lifetime. An account Clerk has already deleted can still be given a server by an ownership transfer, for as long as it takes that deletion to reach us; the server is then deleted with the rest of that account's servers.

Clerk's `id` is who an account is. The primary email address and the picture are both optional at Clerk and both can change, so each is kept exactly as Clerk sends it and is absent when Clerk sends nothing. Every account is kept. A grant is held against the user ID, and the address only finds somebody at the moment they are shared with, so an account without one cannot be found and needs no other rule; and because an address can move from one account to another, two accounts here can hold the same one until the older webhook arrives, which makes sharing by that address refuse rather than choose. This is the model OpenID Connect, Google and GitHub all document: a stable key for identity, and a name as a way to look it up.

Server ownership is stored on the server, separate from memberships. The owner has no membership and holds every permission. A membership gives another user reads and its checked permissions. Rename, power, member management, SSH management, and deletion have independent permissions; new memberships default to every permission the caller can grant. Delegates can grant only permissions they hold and cannot change or remove a member with broader permissions. Only the owner can transfer ownership, to an existing active member; that membership is removed, and the previous owner receives a membership with every permission. The owner cannot leave; deleting the owner's account requests durable server deletion. An operation completes if its requester had the permission when requesting it, even if that permission is removed while the operation runs. A server that is being deleted accepts no change except its own deletion, and one a member makes to their own membership: leaving takes nothing from anybody, and holding somebody to a server that is disappearing serves nothing.

Platform permissions do not restrict direct SSH or filesystem access. Membership removal does not remove native SSH authorizations. SSH entries have no required platform-member association.

An authorized key entry is an occurrence in one file revision, not a key fingerprint: the same key can appear twice with different options, and an edit names the line it changes. Option order is meaningful to OpenSSH, so edits preserve ordered options and every untouched byte. `sshd -T` reports the configuration on disk, not the settings of the running daemon, and `sshd -t` accepts entries that authentication later rejects, so neither validates an entry. An `expiry-time` value without a `Z` suffix uses the server's timezone, and a date without a time means midnight at the start of that date, so new values are written in UTC with `Z` and shown in both forms.

SSH files remain authoritative on the server. Explicit file updates compare observed bytes and metadata, coordinate cooperating writes, replace the file, and verify the result. This is not compare-and-swap against independent editors. An uncertain outcome must not trigger a blind retry or rollback. OpenSSH authentication and sessions retain their native behavior.

One SSH operation owns one authenticated management connection and one deadline. Discovery, reads, writes, and verification open channels on that connection; each file read closes its SFTP channel. A key acceptance check needs a separate authentication exchange because it asks whether another key can sign in. It shares the operation's cancellation signal. Access status records host verification, authentication, and transport closure on the management connection. A file conflict, validation failure, missing guest tool, or refused candidate key does not erase successful management authentication. Remote programs use one command-channel implementation, including bounded output and the point after which a lost write result is uncertain.

Each allocation has a separate backend management key. Its private key is encrypted with an allocation-bound AES-GCM envelope. Cloud-init receives only its public key and a short-lived host key registration token. The server generates its host key locally; authenticated registration pins the public key without trusting the first SSH response. A repeated report can confirm the same key but never replace it; a different key is refused and recorded as a conflict, because it means either a copied bootstrap token or a replaced server. The report URL must be HTTPS, because the token travels in the request body. Both Primary IP addresses are recorded before the server boots, and a report is refused unless it comes from one of them: the proxy in front of the deployment replaces a client's own forwarding headers, and a request that carries its own address header is rejected before it arrives, so a copied token is useless from anywhere else. A server reports over IPv4 or from anywhere inside its IPv6 network. The bootstrap window is 15 minutes, because cloud-init reports within a minute. A member with the SSH permission can renew that window when the server no longer accepts Composery: the panel gives them one program to run on the server, which asks the SSH server for its own key file, host key and port, installs a new management key, removes the one Composery held before, and reports what it found. The new key pair stays pending until that report arrives, so a renewal nobody runs leaves access exactly as it was, and a lost or stale key is replaced rather than kept. Only inside that window may a report replace a pinned host key, and only from the server's own addresses; both conditions, never one. A customer who can no longer reach the server at all is a support case, not a panel feature. Deletion removes the stored secrets after infrastructure cleanup. Host-key registration and provider running state do not establish SSH reachability.

Server names are permanently claimed by one server identity. A server can rename back to its own historical name; other servers cannot claim it, even after deletion. Every claim stays in serverNames, and an old name resolves to the current one. Because a claim never ends, one account may claim a hundred names a day: enough to create a hundred servers at once, and little enough that nobody takes the namespace. The names of exposed ports will come from the same namespace, so a name a customer stops using is spent for good, and a rate that suits creating servers is not evidence about exposing ports. A name is a server's subdomain at `<name>.composery.cloud`, one flat label that server and port names share: one `*.composery.cloud` certificate then covers every name, which a second label below it would not, and a name says which kind it is only by being asked. It follows DNS label rules: `namePattern` restricts it to `[a-z0-9-]`, 3 to 63 characters, encoded as `1+61+1` because 63 is the DNS label limit, and refuses a run of two hyphens because that shape opens punycode (`xn--`) and the IDN homograph attacks punycode enables. Restricting a name to ASCII is also what makes defending against confusable characters tractable: nothing under `namePattern` can leave that alphabet, so folding the small set of ASCII digit-for-letter look-alikes covers every case, without the fuller Unicode confusables table a wider alphabet would need. The same value is also pushed to the server itself, as a Unix hostname, by `convex/ssh/hostname.ts`. The reserved list in `convex/servers/reserved_names.ts` is deliberately large and grouped by why each name is reserved: our own name and a vendor's, a name a protocol or convention defines, a generic infrastructure word, or a third party's brand. `convex/servers/reserved_names.ts` normalizes both a claimed name and every reserved entry before comparing them, dropping hyphens, stripping a trailing digit run, and folding ASCII confusables, so `api-key`, `apikey`, `api7`, and a look-alike spelling such as `paypa1` are all refused for the same reason as their stem. A reserved name is reported as taken.

Rate limits exist to protect the system, not to slow people down: an account may have one server or hundreds. Limits are per user; a global limit would let one attacker block everyone. Expected failures such as a taken name are returned instead of thrown, because a thrown error rolls back the rate limit attempt it counted.

Quotas limit how many servers one user owns and how many the whole deployment holds. Both are counted from the create request until the provider confirms that the infrastructure is absent, and the owner's quota follows an ownership transfer. A missing quota row means a limit of zero, so a deployment creates nothing until an admin sets both. An admin sets quotas today and billing sets the user quota later. The deployment quota stays at or below the Hetzner project's server limit, which the API does not report; Hetzner allows two Primary IPs for each server in that limit and every server uses exactly two, so a separate address quota would only repeat the server quota. Rate limits are separate: they limit how often an account acts, not how much it holds.

Server writes own quota usage through the mutation boundary in `convex/functions.ts`. Triggers update counts on insertion, ownership change, and deletion in the same transaction. The server row remains until provider cleanup completes. Counts stay stored so a capacity check does not scan every server; changing a limit never rewrites usage. All mutations use this boundary, with imports enforced by the linter. A caught trigger failure still aborts the mutation, so a caller cannot commit a row after discarding an accounting error. There is one server quota model, with no generic kind, recount action, or global recount fence. Direct dashboard edits and data imports bypass these application triggers and must not edit the server or quota tables.

Provider API pacing is separate from user admission. Cleanup has reserved worker capacity and its own share of the provider's budget.

The server identity is independent of its allocation backend and provider name. Hetzner resources use an opaque controller identifier, allocation identifier, and resource kind for ownership checks. Human-readable infrastructure names contain no project or deployment name. New allocations resolve the current configuration; existing allocations retain theirs.

Where an allocation is in its life and what is wrong with it are two separate things. Its status is creating, running, stopped, or deleting; deleting is also its deletion intent, and completed deletion removes the row. Each part, the server, its addresses and the rules in front of it, says what was observed. One failure record holds the code, class, count, and start of the failure sequence; `stuck` is calculated from that record. Location comes from the resolved provider specification. Rules an admin took off in the provider's console do not stop unrelated power commands. A server of another type or in another place stops the rest, because it is not the server this allocation recorded.

What a failure means decides what happens next, and how often it has happened decides only how long the wait is. A failure is passing, waiting on something outside, invalid until its configuration changes, of an outcome nobody knows, or our own defect; each has its own schedule, from ten seconds to an hour. Repetition never turns one kind into another, and nothing is ever given up on: an allocation that is stuck says so and is still picked up again, because a customer's server that nobody comes back to is worse than one request an hour. The single exception is an operation whose own deadline has passed, which is over rather than waiting. A request whose outcome nobody knows is the one that is never sent again; the resource is looked for instead, which its own recorded state decides rather than the failure.

A Hetzner create request is recorded as uncertain before it is sent, so a lost response is resolved by looking the resource up, never by sending the request again. Each worker run takes an epoch and a lease; the lease fences database writes, not requests already sent. A result may change its operation's status only while that operation is still the allocation's current one, so a late result cannot finish or block the operation that replaced it. An admin retry takes a new epoch, so an outstanding run cannot undo it. Both Primary IPs are created before the server and deleted after it, and quotas are released only after Hetzner confirms that every owned resource is absent. Inventory scans record unknown resources as findings for an admin and never delete them. Start, graceful stop, and forced stop are separate operations; a graceful stop never becomes a forced one.

An allocation that has settled is never asked about on its own. One look at one server costs two of the 3600 requests a project has in an hour, so looking at each of them every five minutes runs out at about three hundred servers. The inventory scan already reads every server this controller labelled, fifty to a request, so what it sees is written into each allocation instead, and an allocation is woken only when there is work to do. One page every ten seconds costs the same whatever the fleet is, and each page asks for the next one when it is due rather than waiting for a cron, and how long a cycle takes is how old an observation can be, so the scan never stops walking: the last page of a cycle is followed by the first page of the next. The scan writes down only what it saw. An operation belongs to whoever holds the lease, and an allocation that is stuck stays stuck, because seeing the server is no answer to what the work ran into. What one look at a server means is worked out in one place, so the scan and the worker cannot come to different answers about the same server.

The deployment paces itself by what Hetzner says, not by a number of its own. Every reply states the project's limit, what is left, and when all of it is back, and Hetzner gives requests back gradually until then. The deployment keeps the newest of these in one row for the project, because it belongs to the token and not to one run or one process, and it projects what has come back since. When no more than a reserve is left, no run starts until enough has come back to pass it again, which at Hetzner's default is seconds, not the hour a reset would take; the reserve is what the runs already under way can still send. Within the budget, the work and cleanup queues each have a share of the stated limit, so neither starves the other, and the same burst, so that a burst can finish a deletion: taking an allocation apart costs more requests than putting one together, and it is what gives a customer's addresses and quota back. The inventory scan spends the work queue's share. A run is charged the requests it actually sent, once it is over, because only then is the number known; charging a guess before it started made one creation cost three times what it did, and let the deployment make about twenty servers an hour while two thirds of the project's hour went unused. Until Hetzner has answered once, nothing says what the project allows, so the first run finds out, and the work pools' parallelism bounds what starts before then.

Each worker pass returns one explicit outcome, and one transition function produces its allocation, provider, and operation changes together. A stale operation can still report resource identities needed for cleanup, but cannot finish, block, or impose its retry delay on its replacement. The epoch still fences results after a new lease or admin retry. Resource uncertainty is stored because a request can have reached the provider even when no reply arrives; operation status and allocation status cannot answer that question. The queue is retained as an indexed scheduling projection so cleanup has reserved capacity without scanning the fleet.

After every owned resource is confirmed absent, the provider row, SSH access, allocation, server, and quota release change in one transaction. There is no intermediate stored deleted allocation or scheduled provider-record cleanup. Every way of reading an allocation starts from its server, so a server without its allocation would fail every read of it.

Hetzner is the only allocation backend, so lifecycle code calls it directly without a driver registry or stored backend tag. Its resource identities, resolved specification, lease, action, scheduling fields, and native error code remain in `hetznerCloudAllocations`; shared lifecycle and observations stay in `serverAllocations`. Status reads the provider row for location rather than keeping a second location field. This makes status depend on provider-row changes, including lease updates, in exchange for removing a second fact that writers must keep consistent.

Environment files live at the top of the repository, and each name says who reads it. `.env.local` is the app's, because Next reads only `.env`, `.env.local`, `.env.$(NODE_ENV)` and `.env.$(NODE_ENV).local`, and both `convex dev` and `clerk env pull` write that file. `.env.test` is what the tests read, and Bun loads it into every `bun test`, which is why nothing in it is an instruction on its own: a token is a credential, and `HCLOUD_MODE` is what says whether this run wants the real Hetzner or its fake. Each system's switch sits in that system's own prefix, beside the rest of its variables, and names its two states rather than being a flag, because a flag has no spelling that is safe to get wrong. The file holds the default and the environment beats the file, so one run changes its mind with a word in front of the command and the credentials never move. `.env.convex.example` is neither; it lists what a person puts into a deployment's own settings. A file inside the folder it serves was considered and refused: these are read from the directory a command was started in, and nothing looks upwards, so `tests/.env` would be ignored from the repository root and loaded the moment somebody's shell stood in `tests/`. `bun check` holds all three rules, because each mistake is silent.

Clerk's address is the same shape: `CLERK_FAKE_URL` may replace it only when the deployment and the address both answer on this machine alone. A test fills a fake Clerk with accounts, and the webhook route re-reads the account from Clerk rather than trusting the event body, so without this a test would reach the real Clerk. Clerk's own SDK reads the fake's replies but does not check them, so what decides their shape is Clerk's published description, not the SDK.

Hetzner's address is a constant in `hetzner_cloud/api.ts`. `HCLOUD_FAKE_URL` may replace it only when both the deployment and the address answer on this machine alone, so a test can point the deployment at its own fake, and the same variable set on a real deployment changes nothing. A bootstrap report may travel over plain HTTP only to a loopback address, for the same reason: the token stays on the machine that sends it.

A Convex module path accepts only letters, digits, underscores, and periods: the backend refuses `hyphen-probe.js` on push. So Convex modules use snake_case with a directory-specific filename lint rule, and a test that mirrors one keeps its name. Every other file is kebab-case, because a Next.js route folder becomes a URL segment.

Server pages call `auth.protect()` themselves instead of matching routes in the proxy. Clerk deprecates `createRouteMatcher` in favor of checks at the resource.

Self-contained panels use one provisional 8px radius: cards, table frames, toasts, alerts, radio options, and Clerk card-like surfaces. Menus and popovers use a provisional 6px radius. Small buttons and avatars, text controls, badges, and switch tracks use a provisional 4px radius. Medium and large buttons, avatars, and spinners use a provisional 5px radius. Small spinners and switch thumbs use a provisional 2px radius; checkboxes use a provisional 3px radius. Radio controls remain circular. Full-region backgrounds keep their own shape. The glow clipping box and brand icon remain sharp.

A spinner does not turn. One line travels around a rounded square track and eases through each corner, so a wait moves along the shape the controls already have. The app draws the track as one SVG stroke, and `pathLength` makes every track 100 units long, so one lap of keyframes fits every size and every radius. Clerk draws its spinner on one element that only CSS can reach, so its line is an angle that sweeps around a masked border instead. It keeps the lap duration and the line length that the app states, but an angle crosses the corners of a square faster than the sides, so it cannot hold the corner easing.

Two typefaces give two voices. Chakra Petch (`font-brand`, or `font-wordmark` without the size adjustment, which the wordmark's measured metrics need) is for the logo, buttons, labels, and facts such as resource sizes: the places where the product acts or makes a promise. Onest (`font-sans`) is for everything people read, including headings. Chakra Petch alone feels distant to people who have never used a server, and Onest alone does not signal infrastructure. Chakra Petch is loaded at weight 500 only; Onest is variable, with body text at 350 and headings at 550.

Tabler Icons supplies interface icons that the site owns. An icon-only control is the shared `Button` in icon-only mode, not a separate primitive. Clerk keeps the icons and provider marks that its own components render.

Neutral colors use Tailwind palette tokens, not custom values. The page is stone-50 in light mode and stone-950 in dark mode. A surface is white in light mode. In dark mode, it is 25 percent of the distance from the page to stone-900, so the page and surface remain close but distinct in both themes. Interactive dark surfaces use stone-900 on hover and stone-800 while active. Form controls and option rows use the background fill as an inset surface; cards use the surface fill. Static muted fills have their own token, so changing an interaction cannot change a badge or icon box. Each hover or active state is closer to the foreground than the state before it. Structural and control borders share one neutral base token in both themes; only hover, active, and focus states move away from it. A control border moves one palette step for each interaction state, so a light secondary control does not jump from stone-200 to stone-400 on hover. Keyboard focus uses a one-pixel neutral outline for native and Clerk controls. Text inputs have no hover state and use a separate, stronger neutral border while focused. Brand and primary actions use perceptual state steps as large as danger actions. Danger actions use Tailwind red steps: a primary destructive action is filled, while a secondary destructive action starts as red text and gains a quiet red surface on interaction. Components use only semantic tokens, so a color changes in `globals.css` and nowhere else. The raw properties have an `--app-` prefix because embedded components can define generic properties such as `--border` on their own elements; a Tailwind semantic utility must not resolve through a property that another component can shadow.

Every internal link, including the logo, uses one `Link` that fades on hover with the same transition as buttons. An animated underline needs an always-present transparent underline, and Chrome paints it in the selection color when the text is selected.

Components join class names with clsx, not tailwind-merge. A `className` prop adds classes and never overrides the component's own. tailwind-merge does not read the Tailwind theme, so it must be configured by hand for every custom token, and a wrong configuration silently deletes classes, for example `font-body` (a weight) next to `font-sans` (a family).

The theme follows the operating system's light or dark preference. There is no manual toggle, so the server needs no stored preference and the first paint is correct.

SSH features use a POSIX shell, Python 3, and OpenSSH's server tools on the server. The scripts discover executables through the server's own `PATH` and read effective SSH configuration before they act; they do not assume an installation directory. The current SSH key-management command surface is intentionally POSIX and OpenSSH-specific: a Windows guest or another SSH implementation remains a valid customer-controlled server, while this feature reports its command surface as unsupported until a native implementation and oracle exist. Everything about a supported server that can be discovered is asked of the server, never assumed: which accounts exist, which key files apply, and what the SSH server's effective configuration is. The effective dump does not retain quote boundaries, so the scripts pair it with OpenSSH's native debug assignments and refuse an ambiguous key-file partition instead of editing a guessed path; built-in defaults use the effective words when OpenSSH emits no assignment. What cannot be discovered is fixed by construction: cloud-init installs the management key for root, and the server reports its configured Ed25519 host key and port. A customer who moves the SSH port, forbids root login, removes the Ed25519 host key, replaces the operating system, or removes a required tool keeps a working server and loses the SSH features, visibly. The other features do not depend on any of this: power, deletion, quotas and status come from the provider's API.

A key edit names the revision of the file it was planned against, and the server's bytes must still match it. A stale revision is refused, which is also what makes a repeated request safe: the second attempt cannot apply twice, because the first one changed the file. An outcome that the server could not confirm is reported as uncertain and never retried on the caller's behalf.

Composery manages authorized key entries, and nothing else about SSH. It reads the SSH server configuration to learn which key files apply to an account, and never writes that configuration: a wrong setting there locks out every user, including Composery. One permission covers all key management, because anyone who can add a key can sign in and edit the same files by hand; a finer permission would promise a boundary that SSH does not enforce. Discovery states what it cannot know instead of guessing: a key command is a program and its keys cannot be listed, certificate sources are shown separately, and every answer comes from the configuration on disk, which the running daemon need not have reloaded. After an add or an update, Composery asks the running SSH server for the key's acceptance: the SSH protocol lets a client offer a public key without a signature, and the server either refuses it or asks for one, so the question needs no private key and opens no session. The server answers from Composery's address, so a key limited with `from=` is reported as unknown rather than refused, and a failed question never turns a successful write into an error.

SSH host certificates are not built. Pinning at creation protects Composery's own connections, and it is the customer, not Composery, who still meets a trust-on-first-use prompt. A host certificate would fix that, and would turn a legitimate host key change from an incident into a re-signing, but its principal is a name. A server has one, so what remains is a certificate authority to hold and rotate. Revoking a host certificate is not ours to do: the list is a file on the client, so a short lifetime is the control, and only a user certificate would need a list that reaches every server. Nothing built now is wasted: a certificate is one more line in the same file, and the pin stays valid beside it. Decide it with the app naming scheme, not before. `docs/ssh-certificates.md` holds the sketch and the evidence.

A system's published description lives in `contracts/` because it decides whether the harness is correct and must itself be tested. `scripts/contracts.ts` is the only updater; tests read the pins offline. Each pin records the source, date, and digest of the published document. A declared operation list selects native OpenAPI objects and their reference graph. Schema constraints are retained instead of reduced to a language this repository must interpret. Ajv owns schema validation, and the adapter owns the HTTP shapes this harness uses. A shape the adapter cannot check fails before traffic runs. Reference cycles stay in the graph, so recursion never becomes an unconstrained object.

Both halves of an exchange are checked: what Composery sends, and what a fake answers. For Hetzner both halves are ours, since we build the requests by hand. For Clerk the requests come from Clerk's own client, so checking them checks Clerk; what is worth checking there is everything we accept, because the client deserializes a reply without validating it and a fake could invent any field. The Clerk API version is the one that client asks for, and the fake refuses a request carrying another, so an upgrade cannot leave the pinned description behind quietly.

Where a system disagrees with its description, a waiver records the evidence and the exact alternate values it accepts. It names one operation, value location, and schema keyword. It fails when the claim changes or its operation runs without the allowed difference. Each waiver has a reproducer in `tests/contracts/`; neighbouring constraints and values outside the evidence must still fail. This prevents evidence that an image may be a numeric ID from accepting an object, boolean, or invalid ID at the same location.

`SSH_ACCESS_ENCRYPTION_KEYS` is an ordered list rather than one key, and every stored secret names the key that encrypted it in a version prefix that the encryption itself covers. Naming the key is what makes retirement a question the database answers instead of a guess: count what still names the old key. The alternative, trying each key in turn, is simpler and cannot answer it. The order is what expresses the two deployments a safe rotation needs, which two separate variables cannot: a key must be readable everywhere before anything seals with it, or a value written by one deployment cannot be opened by another. `ssh/secrets:reEncrypt` walks the stored values and leaves a row that changed while it ran, because a renewal writes the same fields and its secrets are newer.

A server type Hetzner no longer offers is permanent, like an image it no longer offers, and unlike capacity, which is the other thing a precondition failure at that point would mean. The three were the same status until a test could not tell them apart.

A deprecation Hetzner has announced does not make a thing unusable. Hetzner's `deprecation` carries the day it was announced and the day the thing stops working, and it announces months ahead; `status` is what says whether an image can be used now. Reading the announcement as "gone" would refuse every new server from the day Hetzner says a word about the image we pin, on a date Hetzner chooses. So an image is chosen on its status and on `unavailable_after` being in the future, and a location the same.

A bootstrap token is not single-use. The same report can be accepted more than once until the window closes, because a server retries a report it could not deliver and refusing the second one would leave an allocation with no pinned key. Repeating it changes nothing a first delivery did not: it cannot replace a key that is already pinned, and it is refused from anywhere but the server's own addresses. What ends it is the window, not the count.

Deleting a row is not erasing what it held. A delete takes a document out of the database; it is not a promise that those bytes are gone from every copy underneath. So a stored secret's safety rests on the key that sealed it rather than on the delete, which is why every envelope names its key and why retiring one is a question the database can answer by counting what still names it. What matters is what can no longer be read, not what can no longer be found.

Customers get notices before release. Email is the channel, because it reaches somebody who is not looking at the panel, and the panel says the same thing for somebody who is. The two are one statement in two places rather than two features: an email may be sent again and a panel line is what is true now.

Composery never writes a server's SSH configuration. It reads it, to learn which key files apply. A button that put the configuration back would only work over a connection that works, which is the case where nothing needs putting back, and showing the file invites editing it, which would make Composery an editor of one file for no stated reason. A person with our key and a support case can do it by hand, and that is rare enough to stay a person's job.

Nobody here is listed. Sharing takes an email address, which finds the one account holding it at that moment, and nothing answers "does this person exist" to anybody who types something in. What a panel may show is what that lookup found, which needs a name to have been stored first; none is today.

Nothing repairs a customer's server by itself, and that is not a stage on the way to something that does. A server Composery can no longer reach is a support case: a person decides what happened and what to do, and what they do is theirs to write on the day. What the deployment owes them is that its own state is never hand-rolled: minting a management key, sealing it, and holding the bootstrap window open all happen through the one path that creating a server uses, reachable by a person holding this deployment's key. Rescue at the provider, writing to a mounted disk, and replacing an address are all such cases, so none of them has a feature. An address that has to be replaced leaves the customer with a different one, and telling them afterwards is what is owed; a server that has to be rebooted to attach one is not a thing to do to somebody who is still using it.

A server's addresses are shown, plainly and read-only. Everything a customer does next points at one: a DNS record, a connection string, another machine's allowlist, a reverse proxy's upstream, a monitoring target, and the `known_hosts` entry on every client that ever connected. The case that settles it is the first one: a server can always tell you its own addresses, and you cannot reach a server to ask without one. A name would replace that, and the two kinds of name are not alike. A name for a whole server is entirely outside the server, a record pointing at an address, so nothing the customer does inside can break it. A name for one app is not, because DNS carries no port: reaching one app by hostname needs something routing by Host or SNI, either on the server, where it is state the customer can remove and degrades like the SSH features do, or at Composery's edge, where it does not degrade and Composery carries what the customer put there. `docs/roadmap.md` holds that choice. The reasoning is in [the session that worked it out](sessions/2026-09-14-claude-code-names-funnel-refactoring-and-repository-reorganization.md).

A session in `docs/sessions/` is input, not instruction, whether it informed research, implementation, or naming. `bun run session:import <source>` adds one as `<date>-<reader>-<title>.md`. A session keeps what the person and the assistant said to each other: their text, the questions the assistant asked through a prompt with their answers, and commands, interruptions, compactions, and continuations as session events. It leaves out tool calls and their output, thinking, and what the harness adds, by kind of record and never by judgement of content: git and the current documents hold what the work produced, and a session holds the reasoning between them. A Claude Code session follows its continuations back to the first, and follows the path of messages that Claude Code kept, so a rewound branch is not part of it. A conclusion that a session reaches belongs in the document for its topic.
